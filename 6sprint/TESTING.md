# Тестирование генератора случайных чисел

## Автоматические тесты (pytest)

```bash
pytest tests/test_csprng.py
```

- **Уникальность:** 1000 ключей по 16 байт, дубликатов быть не должно.
- **Распределение:** средняя доля единичных бит в 1000 ключах лежит в диапазоне 49–51 %.
- **Ошибки:** сбой `os.urandom` и «короткое» чтение превращаются в понятное `CSPRNGError`.
- **Запрет `random`:** ни один файл пакета не импортирует модуль `random`.
- **Интеграция:** тесты `tests/test_keygen_cli.py` проверяют, что ключ и все IV берутся из
  `generate_random_bytes`, что ключ печатается в stdout один раз и не попадает в файл с шифртекстом.

## NIST Statistical Test Suite (STS)

### Процедура

1. Подготовка данных (10 МБ, как рекомендовано 1–100 МБ):

   ```bash
   python scripts/generate_nist_data.py --size-mb 10 --output nist_test_data.bin
   ```

2. Получите NIST STS (версия 2.1.x) на сайте NIST (раздел Random Bit Generation →
   Documentation and Software), распакуйте и соберите:

   ```bash
   cd sts-2.1.2
   make
   ```

   Нужен компилятор C. В Windows используйте WSL или Cygwin.

3. Запустите набор, указав длину одной последовательности в битах:

   ```bash
   ./assess 1000000
   ```

   Ответы на запросы (точные формулировки зависят от версии, см. документацию STS):

   | Запрос | Ответ |
   | --- | --- |
   | Generator Selection | `0` (Input File), затем путь к `nist_test_data.bin` |
   | Statistical Tests | `1` (Apply All Statistical Tests, все 15 тестов) |
   | Parameter Adjustments | `0` (оставить значения по умолчанию) |
   | How many bitstreams? | `80` (10 МБ = 80 000 000 бит = 80 последовательностей по 10^6 бит) |
   | Input File Format | `1` (Binary) |

4. Результаты находятся в `experiments/AlgorithmTesting/finalAnalysisReport.txt`.

### Критерии успеха

- Для каждой последовательности и теста p-значение ≥ 0.01 означает «пройдено».
- Доля прошедших последовательностей для каждого теста должна лежать в интервале
  `p̂ ± 3·√(p̂(1 − p̂)/m)`, где `p̂ = 0.99`, `m` — число последовательностей (для `m = 80`: от 0.9566 до 1).
- Равномерность p-значений (столбец P-VALUE в отчёте) должна быть ≥ 0.0001.
- Единичные неудачи статистически ожидаемы; массовые провалы означают дефект генератора.

## Быстрая самопроверка без STS

Скрипт `scripts/quick_stats.py` реализует три теста из NIST SP 800-22 (Frequency/monobit, Runs,
Cumulative Sums в прямом и обратном направлении) на чистом Python. **Это не официальный STS**
и не заменяет его: проверяется лишь 3 из 15 тестов. Формулы проверены на опубликованном примере
из NIST SP 800-22 (p-значения 0.109599, 0.500798, 0.219194 и 0.114866 воспроизводятся точно,
см. `tests/test_quick_stats.py`).

```bash
python scripts/generate_nist_data.py --size-mb 10 --output nist_test_data.bin
python scripts/quick_stats.py nist_test_data.bin
```

Результат одного из запусков (10 МБ, 80 последовательностей по 1 000 000 бит, α = 0.01):

| Тест | Прошло | Допустимый минимум | min p | Среднее p |
| --- | --- | --- | --- | --- |
| frequency (monobit) | 78/80 | 77/80 | 0.0053 | 0.5268 |
| runs | 80/80 | 77/80 | 0.0354 | 0.4932 |
| cumulative sums (forward) | 77/80 | 77/80 | 0.0015 | 0.5061 |
| cumulative sums (reverse) | 78/80 | 77/80 | 0.0035 | 0.5152 |

Все доли прошедших последовательностей попадают в допустимый интервал, а средние p-значения
близки к 0.5, как и ожидается для равномерного распределения. Данные генерируются заново при каждом
запуске, поэтому точные числа от запуска к запуску меняются.

## Тестирование хеш-функций (спринт 4)

Реализации `sha256` и `sha3-256` (папка `src/cryptocore/hash/`) проверяются так:

| Требование | Что проверено | Где |
| --- | --- | --- |
| TEST-1 | Векторы NIST: пустая строка, `abc`, 448-битное и 896-битное сообщения, миллион символов `a`; константы SHA-256 и Keccak | `tests/test_sha256.py`, `tests/test_sha3_256.py` |
| TEST-2 | Пустой файл: `e3b0c442…b855` (SHA-256), `a7ffc6f8…434a` (SHA3-256) | `tests/test_dgst_cli.py` |
| TEST-3 | Вывод `cryptocore dgst` совпадает побайтово с `sha256sum --text` и значением `openssl dgst -sha3-256` | `tests/test_dgst_cli.py` |
| TEST-4 | Файл 1 100 000 000 байт (больше 1 ГБ), см. ниже | `tests/test_hash_large_file.py` |
| TEST-5 | Лавинный эффект: изменение одного бита меняет около половины бит хеша | `tests/test_hash_avalanche.py` |
| TEST-6 | Сравнение скорости с `hashlib` и `sha256sum` | `scripts/benchmark_hash.py` |

Дополнительно проверяются границы дополнения (длины 0, 55, 56, 63, 64, 65 для SHA-256 и 135, 136, 137 для SHA3-256),
независимость результата от размера порций, чтение входа только порциями по 8192 байта и ограниченный размер
внутреннего буфера. Реализации сверяются с `hashlib` на случайных данных разной длины.

Из-за отсутствия утилит `sha3sum` и `b2sum` в тестовой среде SHA3-256 сверялся с `openssl dgst -sha3-256`.
Алгоритм BLAKE2b не реализован: по HASH-2 достаточно одного второго алгоритма (выбран SHA3-256).

### Файл больше 1 ГБ (TEST-4)

Тест создаёт файл из 1 100 000 000 байт случайных данных, параллельно считает эталонный хеш через `hashlib`
и сравнивает его с результатом `hash_stream` (чтение порциями по 8192 байта). Тест долгий, поэтому по
умолчанию пропускается:

```bash
CRYPTOCORE_LARGE_TEST=1 python -m pytest tests/test_hash_large_file.py
```

Результат запуска:

| Алгоритм | Размер файла | Время | Хеш совпал с hashlib | Рабочая память процесса |
| --- | --- | --- | --- | --- |
| sha256 | 1 100 000 000 байт | 36 мин 32 с | да | около 35 МБ |
| sha3-256 | 1 100 000 000 байт | 35 мин 16 с | да | около 35 МБ |

Рабочая память (~35 МБ) складывается из интерпретатора, библиотеки pycryptodome и блока данных, который тест
использует для генерации файла; она не росла по мере хеширования, то есть расход памяти не зависит от размера файла.

### Лавинный эффект (TEST-5)

Для каждого алгоритма изменялся один бит случайного 64-байтового сообщения (200 попыток); в идеале меняется 128 бит из 256.

| Алгоритм | В среднем изменилось бит | Минимум | Максимум |
| --- | --- | --- | --- |
| sha256 | 127,4 | 107 | 153 |
| sha3-256 | 126,9 | 103 | 150 |

### Скорость (TEST-6)

```bash
python scripts/benchmark_hash.py --sizes-mb 0.1 1 4
```

Измерения на одной машине (CPython 3.12), одновременно работали другие нагрузки, поэтому цифры ориентировочные.
`sha256sum` для малых файлов упирается в запуск процесса.

| Алгоритм | Размер, МБ | cryptocore, с | hashlib, с | sha256sum, с | Скорость cryptocore, МБ/с | Медленнее hashlib в |
| --- | --- | --- | --- | --- | --- | --- |
| sha256 | 0,1 | 0,246 | 0,00012 | 0,048 | 0,41 | ~2000 |
| sha256 | 1 | 2,301 | 0,00068 | 0,046 | 0,43 | ~3400 |
| sha256 | 4 | 9,560 | 0,00244 | 0,057 | 0,42 | ~3900 |
| sha3-256 | 0,1 | 0,210 | 0,00035 | - | 0,48 | ~600 |
| sha3-256 | 1 | 2,431 | 0,00403 | - | 0,41 | ~600 |
| sha3-256 | 4 | 8,740 | 0,01530 | - | 0,46 | ~570 |

Собственные реализации на чистом Python работают со скоростью около 0,4–0,5 МБ/с, на 3 порядка медленнее
оптимизированных библиотек на C. Для учебных целей это приемлемо, но файл в 1 ГБ хешируется около получаса.

## Тестирование MAC (спринт 5)

HMAC (`src/cryptocore/mac/hmac.py`) и бонусный AES-CMAC (`src/cryptocore/mac/cmac.py`) проверяются так:

| Требование | Что проверено | Где |
| --- | --- | --- |
| TEST-1 | Векторы RFC 4231, раздел 4 (HMAC-SHA-256): случаи 1, 2, 3, 4, 6, 7 и усечённый случай 5 | `tests/test_hmac.py` |
| TEST-2 | Программа проверяет HMAC, который сама создала (`--verify`, код возврата 0) | `tests/test_dgst_mac_cli.py` |
| TEST-3 | Изменение одного бита файла: проверка завершается кодом 1 и сообщением `[ERROR] HMAC verification failed` | `tests/test_dgst_mac_cli.py` |
| TEST-4 | Другой ключ: проверка завершается кодом 1 | `tests/test_dgst_mac_cli.py` |
| TEST-5 | Ключи короче блока (1, 16 байт), равные блоку (64 байта) и длиннее (100, 131, 200 байт); все длины 0–139 байт сверены со стандартной библиотекой | `tests/test_hmac.py`, `tests/test_dgst_mac_cli.py` |
| TEST-6 | Пустой файл и пустое сообщение | `tests/test_hmac.py`, `tests/test_dgst_mac_cli.py` |
| TEST-7 | Файл больше 1 ГБ, см. ниже | `tests/test_mac_large_file.py` |
| TEST-8 | Векторы NIST SP 800-38B / RFC 4493 для AES-CMAC (длины 0, 16, 40, 64 байта) и подключи K1, K2 | `tests/test_cmac.py` |

Дополнительно: HMAC сверяется с `hmac` из стандартной библиотеки Python (для SHA-256 и SHA3-256), CMAC — с
pycryptodome (длины 0–69, 160, 1000 байт). Через интерфейс `dgst` и HMAC, и CMAC сверяются с OpenSSL
(`openssl dgst -sha256 -mac HMAC -macopt hexkey:...` и `openssl mac -cipher AES-128-CBC ... CMAC`).
Результат не зависит от размера порций, на которые разбит вход. Файл с ожидаемым значением разбирается гибко
(регистр, пробелы, переводы строки Windows и Unix, имя файла); пустой, нетекстовый и «не шестнадцатеричный» файлы дают
ошибку с ненулевым кодом. Для CLI также проверены ошибки: нет `--key`, ключ не в hex, `--verify` без `--hmac`,
`--verify` вместе с `--output`, `--hmac` вместе с `--cmac`.

### Файл больше 1 ГБ (TEST-7)

Тест создаёт файл из 1 100 000 000 байт случайных данных, параллельно считает эталон (`hmac` стандартной библиотеки
для HMAC-SHA-256 с ключом 100 байт и pycryptodome для AES-CMAC) и сравнивает его с результатом собственной реализации,
которая читает файл порциями по 8192 байта. Тест долгий, поэтому по умолчанию пропускается:

```bash
CRYPTOCORE_LARGE_TEST=1 python -m pytest tests/test_mac_large_file.py
```

Результат запуска:

| Алгоритм | Размер файла | Время | Значение совпало с эталоном | Рабочая память процесса |
| --- | --- | --- | --- | --- |
| HMAC-SHA-256 (ключ 100 байт) | 1 100 000 000 байт | 24 мин 35 с | да | около 37 МБ |
| AES-CMAC | 1 100 000 000 байт | 2 мин 16 с | да | не измерялась отдельно, в тесте используется та же схема чтения порциями |

Память HMAC (~37 МБ) складывается из интерпретатора, pycryptodome и блока данных, используемого тестом для генерации
файла; она не росла по мере обработки файла, то есть не зависит от его размера.

Плюс сетка: nonce 1, 8, 12, 16, 60 байт x AAD 0–100 байт x данные 0–257 байт сверена с pycryptodome (315 комбинаций); ключи 128, 192, 256 бит | `tests/test_gcm.py` |
| TEST-2 | Шифрование и расшифрование с тем же AAD возвращает исходные данные (библиотека и CLI, размеры 0–4096 байт) | `tests/test_gcm.py`, `tests/test_gcm_cli.py` |

| TEST-5 | 1000 вызовов `encrypt` дают 1000 разных nonce по 12 байт; nonce берётся из `generate_random_bytes`; в CLI каждый запуск даёт новый nonce | `tests/test_gcm.py`, `tests/test_gcm_cli.py` |
| TEST-6 | Пустой AAD (аргумент не указан, `--aad ""`) и пустые данные | `tests/test_gcm.py`, `tests/test_gcm_cli.py` |
| TEST-7 | AAD больше памяти: передаётся итератором кусков, см. ниже | `tests/test_gcm.py`, `tests/test_gcm_large_aad.py` |
| TEST-8 | Сверка с pycryptodome и с библиотекой `cryptography` (на базе OpenSSL) в обе стороны, в том числе для файлов, созданных CLI | `tests/test_gcm.py`, `tests/test_gcm_cli.py` |
| TEST-9 | Encrypt-then-MAC: все режимы (ctr, cbc, cfb, ofb), перебор каждого бита, неверный AAD и ключ, граница между шифртекстом и AAD, разделение ключей, проверка тега до расшифрования; HKDF по вектору RFC 5869 | `tests/test_etm.py` |

Дополнительно проверены: свойства умножения в GF(2^128) (единица, коммутативность, дистрибутивность), совпадение
табличного умножения с побитовым алгоритмом NIST, nonce нестандартной длины, разбиение AAD на куски любого размера,
формат файла `nonce || шифртекст || тег`, явный `--iv`/`--nonce` (в том числе пример из ТЗ с нулевым ключом и
нулевым nonce), ошибки аргументов (`--aad` не в hex, `--aad` не для режима gcm, nonce не 12 байт) и коды возврата.

Утилита `openssl enc` режимы AEAD не поддерживает (`enc: AEAD ciphers not supported`), поэтому команда
`openssl enc -aes-128-gcm ...` из ТЗ неприменима. Вместо неё OpenSSL используется через библиотеку `cryptography`.

### AAD больше памяти (TEST-7)

AAD подаётся генератором кусков по 1 МБ и нигде не накапливается. Запуск:

```bash
CRYPTOCORE_LARGE_TEST=1 python -m pytest tests/test_gcm_large_aad.py
```

| Проверка | Объём AAD | Время | Результат |
| --- | --- | --- | --- |
| GCM: шифрование (тег совпал с pycryptodome, который тоже получал AAD по частям) и расшифрование | 1 100 000 000 байт | 3 мин 53 с | пройден |
| Encrypt-then-MAC: шифрование и расшифрование | 50 000 000 байт | 2 мин 26 с | пройден |

Рабочая память процесса в ходе теста оставалась около 38 МБ и не росла с объёмом AAD. Для Encrypt-then-MAC взят меньший
объём, потому что собственный HMAC обрабатывает около 0,45 МБ/с. Обычные тесты проверяют ту же логику на 3 МБ.

Скорость GCM на чистом Python: около 5 МБ/с на шифровании и около 14 МБ/с на обработке AAD.
